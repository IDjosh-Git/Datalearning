SQL Foundations & First Queries

Understand relational data and write your first SELECT statements.

Beginner

1. Database Concepts

  • A database stores structured data.
  • A table contains rows and columns.
  • A row represents one record.
  • A column represents one attribute.
  • A primary key uniquely identifies a row.

2. SELECT and FROM

  • SELECT chooses columns.
  • FROM chooses the table.
  • Use * only when intentionally returning every column.
  • Terminate statements with semicolons where the platform supports it.

3. Aliases

  • Use AS to give a column a friendly output name.
  • Aliases improve readability.
  • Avoid spaces or reserved words unless your SQL dialect handles them appropriately.

4. Basic Query Reading

  • Read SQL in logical pieces.
  • Formatting improves comprehension.
  • Keywords are commonly capitalized by convention, although most dialects are case-insensitive for keywords.

🎯 Week Goal

Understand basic database terms and retrieve selected columns from a table.

🧪 Weekly Practice

  1. Create or use a sample Customers table.
  2. Return every column.
  3. Return only CustomerID, CustomerName and City.
  4. Alias CustomerName as Customer.
  5. Write five simple SELECT queries.

💡 Teaching Tip

Do not memorize SQL as one long sentence. Read each clause as a separate instruction.

Filtering, Conditions & Sorting

Return only the rows that answer the business question.

Querying

1. WHERE

  • WHERE filters rows.
  • Use =, <>, >, <, >=, <=.
  • Text values are usually written inside quotes.
  • Date-literal syntax depends on the database dialect.

2. AND / OR / NOT

  • AND requires both conditions.
  • OR accepts either condition.
  • Use parentheses when combining AND and OR.
  • NOT reverses a condition.

3. IN, BETWEEN, LIKE

  • IN checks a list of values.
  • BETWEEN tests an inclusive range in many SQL dialects.
  • LIKE searches patterns.
  • % commonly means any number of characters.

4. ORDER BY

  • Sort ascending with ASC.
  • Sort descending with DESC.
  • Use multiple sort columns.
  • ORDER BY normally appears near the end of a SELECT query.

🎯 Week Goal

Use WHERE conditions safely and sort result sets deliberately.

  4. Find products with names starting with 'S'.
  5. Sort Revenue descending.

When combining AND and OR, use parentheses so the intended logic is obvious.

Aggregations & Grouped Analysis

Turn transaction rows into business summaries.

Analysis

1. Aggregate Functions

  • COUNT counts rows/values depending on syntax.
  • SUM adds numeric values.
  • AVG calculates an average.
  • MIN and MAX find extremes.

2. GROUP BY

  • GROUP BY creates one result group per unique combination.
  • Every non-aggregated selected column normally belongs in GROUP BY.
  • Grouping level determines the granularity of the result.

3. HAVING

  • WHERE filters rows before grouping.
  • HAVING filters grouped results after aggregation.
  • Use HAVING for conditions such as SUM(Revenue) > 1000000.

4. Distinct Counts

  • COUNT(DISTINCT CustomerID) counts unique customers in supported dialects.
  • Know the difference between rows, orders, and customers.
  • Define the business grain before counting.

Calculate totals, averages and counts by business categories.

Always ask: what does one row of my grouped result represent?

  3. Calculate COUNT(*).
  4. Calculate MIN and MAX Revenue.

GROUP BY
Explain it simply: GROUP BY changes one overall total into a total for each category.
Step by step
  1. Group Revenue by Region.
  2. Add COUNT(*) as order-row count.
  3. Group by Region and Status.
  4. Explain that Region+Status creates a finer grain than Region alone.
  5. Sort grouped results by TotalRevenue DESC.

WHERE vs HAVING
Explain it simply: WHERE filters detail rows before aggregation; HAVING filters aggregate groups after the groups exist.
Step by step
  1. Filter Orders to Completed in WHERE.
  2. Group by Region.
  3. Calculate SUM(Revenue).
  4. Use HAVING SUM(Revenue) > 1000000.
  5. Compare the role of WHERE and HAVING.
SELECT Region, SUM(Revenue) AS TotalRevenue FROM Orders WHERE Status = 'Completed' GROUP BY Region HAVING SUM(Revenue) > 1000000;
Learner task: Return Salespeople with at least 20 completed orders.
Common mistake: Using HAVING for simple row-level filters makes intent less clear and can be less efficient.
Session recap: Filter early with WHERE when possible; use HAVING for grouped conditions.

Joining Tables

Combine related data from normalized tables.

Relationships

1. Keys

  • Primary key uniquely identifies a row.
  • Foreign key references a key in another table.
  • Join columns should represent the same business key.
  • Data types should be compatible.

2. INNER JOIN

  • Returns matching rows from both sides.
  • Non-matching rows are excluded.
  • Useful when only matched entities are required.

3. LEFT JOIN

  • Returns all rows from the left table.
  • Matching data is added from the right table.
  • Unmatched right-side columns become NULL.
  • Useful for identifying missing matches.

4. Join Quality

  • One-to-many joins can multiply rows by design.
  • Many-to-many joins can create unexpected duplication.
  • Always validate row counts and totals after a join.

🎯 Week Goal

Join fact and dimension-style tables correctly without accidentally losing or duplicating rows.

CASE Expressions, NULLs & Data Cleaning

Create business classifications and handle missing values safely.

Data Quality

1. CASE

  • CASE creates conditional output.
  • Use it for bands, labels and status categories.
  • Order conditions from specific to general.
  • Provide an ELSE where appropriate.

2. NULL

  • NULL means missing/unknown, not zero and not empty text.
  • Use IS NULL and IS NOT NULL.
  • Aggregates often ignore NULL values except COUNT(*).
  • Interpret missingness using business context.

3. COALESCE

  • Returns the first non-NULL value.
  • Useful for controlled fallback display.
  • Do not blindly replace unknown measures with zero.

4. Basic Cleaning

  • TRIM removes extra surrounding spaces in many dialects.
  • UPPER/LOWER standardize case.
  • String/date function names differ somewhat by database platform.

Use CASE and NULL-handling functions to produce analysis-ready fields.

Subqueries & Common Table Expressions

Break complex analysis into understandable steps.

Query Structure

1. Subqueries

  • A subquery is a query inside another query.
  • It can appear in WHERE, FROM, or SELECT depending on the use case.
  • Correlated subqueries reference the outer query and may be more expensive.

2. CTEs

Window Functions for Analytical SQL

Calculate rankings, running totals, and prior-period comparisons without collapsing rows.

Intermediate

1. OVER

  • Window functions use OVER(...).
  • PARTITION BY creates independent groups.
  • ORDER BY inside OVER defines sequence.
  • Rows remain visible.

2. ROW_NUMBER & RANK

  • ROW_NUMBER gives unique sequential positions.
  • RANK leaves gaps after ties.
  • DENSE_RANK does not leave gaps after ties.

3. Running Totals

  • SUM(...) OVER can create cumulative values.
  • Ordering is essential.
  • Partition by Region for separate running totals per Region.

4. LAG & LEAD

  • LAG accesses a prior row value.
  • LEAD accesses a later row value.
  • Useful for period-over-period comparisons.

ROW_NUMBER, RANK and DENSE_RANK
Explain it simply: Window ranking adds a position to rows without grouping them away.
Step by step

Query Quality, Performance & Validation

Write SQL that is correct, maintainable, and conscious of performance.

Professional Practice

1. Query Quality

  • Use explicit columns.
  • Use readable formatting.
  • Use meaningful aliases.
  • Comment unusual business logic.
  • Keep filters as selective as the question allows.

2. Performance Concepts

  • Indexes can help the database locate rows efficiently.
  • Functions on filtered columns can sometimes prevent efficient index use depending on platform.
  • Large joins and sorts can be expensive.
  • Execution plans explain how the database intends to run a query.

3. Validation

  • Compare row counts before and after joins.
  • Reconcile totals.
  • Check duplicates at expected unique grains.
  • Test edge cases and NULLs.

4. Safe Data Work

  • SELECT is read-oriented; INSERT/UPDATE/DELETE change data.
  • Use transaction and environment controls appropriate to your system.
  • Never test destructive statements casually on production data.
