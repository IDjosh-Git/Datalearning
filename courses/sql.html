SQL Foundations & First Queries

Understand relational data and write your first SELECT statements.

Beginner

1. Database Concepts

  • A database stores structured data.
  • A table contains rows and columns.
  • A row represents one record.
  • A column represents one attribute.
  • A primary key uniquely identifies a row.

2. SELECT and FROM

  • SELECT chooses columns.
  • FROM chooses the table.
  • Use * only when intentionally returning every column.
  • Terminate statements with semicolons where the platform supports it.

3. Aliases

  • Use AS to give a column a friendly output name.
  • Aliases improve readability.
  • Avoid spaces or reserved words unless your SQL dialect handles them appropriately.

4. Basic Query Reading

  • Read SQL in logical pieces.
  • Formatting improves comprehension.
  • Keywords are commonly capitalized by convention, although most dialects are case-insensitive for keywords.

01 · The business reason — why this matters

A retail manager asks which orders were completed. A database stores repeated transactions consistently, and SQL retrieves the precise rows required for the decision.

02 · How it actually works

A table has a row grain (one order here), typed columns, and an identifying key. SELECT chooses columns, FROM chooses the table, WHERE restricts rows, and ORDER BY makes presentation deterministic. The engine parses SQL, builds a query plan, and evaluates it on stored rows.

Learn it step by step — simple explanation

Picture it this way: Think of a database table as a register: each row is one order, and each column answers one fixed question about that order. The order ID identifies a record; it is not a calculation.

Follow the logic in three small steps
  1. Open the orders table and inspect column names
  2. Ask what one row represents before doing any sums
  3. Choose only the columns needed, restrict the completed orders, then sort by order_id
Read the expected result: In the first displayed record, quantity 2 and unit price 150000 describe order 1001; the query has not yet multiplied them. LIMIT 3 limits the display, not the actual database.
Now try it without copying: Change LIMIT 3 to LIMIT 5 and explain why five rows qualify even though the input has six.

SELECT order_id, customer, quantity, unit_price
FROM orders
WHERE status = 'Completed'
ORDER BY order_id

Filtering, Conditions & Sorting

Return only the rows that answer the business question.

Querying

1. WHERE

  • WHERE filters rows.
  • Use =, <>, >, <, >=, <=.
  • Text values are usually written inside quotes.
  • Date-literal syntax depends on the database dialect.

2. AND / OR / NOT

  • AND requires both conditions.
  • OR accepts either condition.
  • Use parentheses when combining AND and OR.
  • NOT reverses a condition.

3. IN, BETWEEN, LIKE

  • IN checks a list of values.
  • BETWEEN tests an inclusive range in many SQL dialects.
  • LIKE searches patterns.
  • % commonly means any number of characters.

4. ORDER BY

  • Sort ascending with ASC.
  • Sort descending with DESC.
  • Use multiple sort columns.
  • ORDER BY normally appears near the end of a SELECT query.

01 · The business reason — why this matters

Teams often ask for one region, one status, and a minimum transaction size; incorrect AND/OR logic quietly changes reported sales.

02 · How it actually works

WHERE evaluates a Boolean condition per row, before grouping. AND binds more tightly than OR, so brackets communicate the intended condition. Text equality and numeric comparisons differ; NULL requires IS NULL, not = NULL.

Learn it step by step — simple explanation

Picture it this way: A WHERE filter is a set of admission rules for individual rows. The database checks those rules before performing any totals; ORDER BY decides how the surviving rows are displayed.

Follow the logic in three small steps
  1. State each condition in plain language
  2. Add parentheses around combined AND/OR tests
  3. Sort the filtered result by a meaningful column and then a stable tie-break
Read the expected result: Compare the order IDs returned, not just the count. The same five completed transactions can appear in different display orders without changing the business answer.
Now try it without copying: Show completed orders from East or West; then change the logic to East AND West and describe why no single-region order qualifies.
03 · Worked example
SELECT order_id, region, quantity * unit_price AS gross_value
FROM orders
WHERE status='Completed' AND region IN ('East','West')
  AND quantity * unit_price >= 40000
ORDER BY gross_value DESC, order_id;
Expected result / verification
order_id | region | gross_value
1001     | East   | 300000
1005     | West   | 150000
1002     | West   | 40000
💡 Industry pro tip

Filter timestamps with an inclusive start and exclusive next-day boundary for portable date ranges.

⚠️ Common beginner trap

WHERE region='East' OR region='West' AND status='Completed' also admits returned East orders.

📌 Key takeaways / cheat sheet
  • Filter before aggregation
  • parenthesize mixed conditions
  • sort using an explicit tie-break.

Aggregations & Grouped Analysis

Turn transaction rows into business summaries.

Analysis

1. Aggregate Functions

  • COUNT counts rows/values depending on syntax.
  • SUM adds numeric values.
  • AVG calculates an average.
  • MIN and MAX find extremes.

2. GROUP BY

  • GROUP BY creates one result group per unique combination.
  • Every non-aggregated selected column normally belongs in GROUP BY.
  • Grouping level determines the granularity of the result.

3. HAVING

  • WHERE filters rows before grouping.
  • HAVING filters grouped results after aggregation.
  • Use HAVING for conditions such as SUM(Revenue) > 1000000.

4. Distinct Counts

  • COUNT(DISTINCT CustomerID) counts unique customers in supported dialects.
  • Know the difference between rows, orders, and customers.
  • Define the business grain before counting.

01 · The business reason — why this matters

A performance dashboard must reconcile to finance: one returned order must not inflate completed-order revenue.

02 · How it actually works

GROUP BY forms one group per region; SUM reduces rows to a metric. WHERE removes unqualified transactions before aggregation; HAVING filters completed groups. Here completed gross revenue is quantity × unit price for Completed rows; this is not net revenue. Real reporting must also define taxes, discounts, refunds and returns.

Learn it step by step — simple explanation

Picture it this way: An aggregate compresses many qualifying orders into a summary. Decide the group (region) and the unit (currency value) before writing SUM, AVG or COUNT.

Follow the logic in three small steps
  1. Filter to completed sales so returns are not treated as positive revenue
  2. Calculate revenue per order as quantity × unit_price
  3. Group by region and reconcile region totals back to 578000
Read the expected result: East 316000 + West 190000 + North 72000 = 578000. These are gross order values; profit uses a different formula: quantity × (unit_price − unit_cost).
Now try it without copying: Add profit per region, reconcile to 135000, and explain the difference between gross revenue and profit.
03 · Worked example
SELECT region, COUNT(*) AS completed_orders,
       SUM(quantity*unit_price) AS revenue
FROM orders
WHERE status='Completed'
GROUP BY region
ORDER BY revenue DESC;
Expected result / verification
region | completed_orders | revenue
East   | 2                | 316000
West   | 2                | 190000
North  | 1                | 72000

⚠️ Common beginner trap

Joining Tables

Combine related data from normalized tables.

Relationships

1. Keys

  • Primary key uniquely identifies a row.
  • Foreign key references a key in another table.
  • Join columns should represent the same business key.
  • Data types should be compatible.

2. INNER JOIN

  • Returns matching rows from both sides.
  • Non-matching rows are excluded.
  • Useful when only matched entities are required.

3. LEFT JOIN

  • Returns all rows from the left table.
  • Matching data is added from the right table.
  • Unmatched right-side columns become NULL.
  • Useful for identifying missing matches.

4. Join Quality

  • One-to-many joins can multiply rows by design.
  • Many-to-many joins can create unexpected duplication.
  • Always validate row counts and totals after a join.

Join fact and dimension-style tables correctly without accidentally losing or duplicating rows.

Joins and relationship cardinality

By the end, you can: Enrich facts without accidentally duplicating revenue.

YOUR MODULE 04 CHECKPOINTSuggested session: 30–60 min + independent practice

Prerequisite: This module builds on the previous module. Objective: Enrich facts without accidentally duplicating revenue.

Apply independently: Create an unmatched-customer report using LEFT JOIN and WHERE c.customer_id IS NULL; state what zero means.

What to produce: Join to customers without increasing the five completed orders; document key cardinality.

How to check: Compare with the worked result shown below, test one changed input or filter, and explain a possible failure or misleading interpretation. A checked lesson is your own declaration of practice—not an automatically graded project.

Try related SQL Arena challenge ↗Validation and project rubric ↗
01 · The business reason — why this matters

Order records may hold a customer_id while the customer segment sits in a separate table; analyses need reliable dimension joins.

02 · How it actually works

JOIN matches related keys. One-to-many means a customer can have many orders; many-to-many or duplicate dimension keys can multiply rows. An INNER JOIN keeps matches, while LEFT JOIN keeps all rows on the left and flags unmatched reference data.

Learn it step by step — simple explanation

Picture it this way: A JOIN is like looking up a customer’s segment using a customer ID. The danger is that matching two or more customer rows to one order can copy its revenue multiple times.

Follow the logic in three small steps
  1. Write down the unique key on each side of the join
  2. Check customer IDs for duplicates before joining
  3. Compare order count and revenue before and after the join
Read the expected result: A LEFT JOIN preserves orders even when no customer record matches. The segment is extra context; the order amount must not change because of the lookup.
Now try it without copying: Create an unmatched-customer report using LEFT JOIN and WHERE c.customer_id IS NULL; state what zero means.
03 · Worked example
SELECT o.order_id, c.segment, o.quantity*o.unit_price AS revenue
FROM orders AS o
LEFT JOIN customers AS c ON o.customer_id=c.customer_id
WHERE o.status='Completed'
ORDER BY o.order_id LIMIT 3;
Expected result / verification
order_id | segment  | revenue
1001     | Consumer | 300000
1002     | Business | 40000
1004     | Business | 72000

A fast incorrect report is worse than a slower audited one; reliability comes before indexing and speed work.

02 · How it actually works

Start with expected row counts, distinct keys, nulls and reconciliations. EXPLAIN QUERY PLAN describes access paths and joins. Indexes can improve selective lookups but add storage and write overhead; on small training datasets a full scan may be optimal.

Learn it step by step — simple explanation

Picture it this way: Validation is the safety check before optimization. A query that returns quickly but duplicates transactions is still incorrect.

Follow the logic in three small steps
  1. Check total row count and distinct order IDs
  2. Check the five qualifying completed records and their combined revenue
  3. Only then inspect EXPLAIN QUERY PLAN or try an index
Read the expected result: The input has six order rows, six distinct order IDs and 578000 in completed revenue. Keep these numbers as independent controls after any rewrite.
Now try it without copying: Intentionally join orders to a duplicate reference table, then use row counts to diagnose inflated totals.
03 · Worked example
SELECT COUNT(*) AS row_count,
 COUNT(DISTINCT order_id) AS unique_orders,
 SUM(CASE WHEN status='Completed'
          THEN quantity*unit_price ELSE 0 END) AS revenue
FROM orders;
Expected result / verification
row_count | unique_orders | revenue
6         | 6             | 578000
💡 Industry pro tip

Keep the validation query beside the production query; rerun both after any optimization.

⚠️ Common beginner trap

EXPLAIN output is platform-specific, and an index is not inherently better for tiny tables.

Applied unit 1

Query trustworthy records

Learning objectives

Understand keys, nulls, filters, and joins; explain why row counts change.

Workplace use case

Investigate orders and customers while preserving unmatched records.

Guided practice

  1. Profile tables
  2. SELECT filtered columns
  3. LEFT JOIN on customer_id
  4. COUNT rows before and after.

Worked example

SELECT o.order_id, c.customer_name
FROM orders AS o
LEFT JOIN customers AS c ON c.customer_id = o.customer_id
WHERE o.order_date >= '2026-01-01';

Assessment checkpoint

What is the difference between WHERE and ON for an outer join? Provide a row-count comparison.

Applied unit 2

Aggregate and validate metrics

Learning objectives

Group by useful dimensions; calculate revenue; handle nulls and divide-by-zero safely.

Workplace use case

Find the top five product categories by realized revenue.

Guided practice

  1. Check order status
  2. join order_items
  3. aggregate with SUM
  4. sort
  5. compare with raw transactions.

Worked example

SELECT category, SUM(quantity * unit_price) AS revenue
FROM order_items
WHERE status = 'completed'
GROUP BY category
ORDER BY revenue DESC
LIMIT 5;

Assessment checkpoint

Explain why grouping by category does not guarantee unique transaction counts.

Applied unit 3

Analyze patterns with windows

Learning objectives

Use CTEs, ROW_NUMBER, and running totals without collapsing detail.

Workplace use case

Rank monthly customer revenue and identify repeat purchasers.

Guided practice

  1. Create monthly CTE
  2. sum revenue per customer
  3. window-rank within each month
  4. inspect ties.

Worked example

WITH monthly AS (
 SELECT customer_id, DATE_TRUNC('month',order_date) AS month, SUM(total) AS revenue
 FROM orders GROUP BY 1,2
) SELECT *, DENSE_RANK() OVER (PARTITION BY month ORDER BY revenue DESC) AS rank_in_month FROM monthly;

Assessment checkpoint

When should you use DENSE_RANK rather than ROW_NUMBER? Provide an example with tied revenue.
