Detailed teaching sessions & worked examples

Session 1 — What AI does and does not do (75 minutes)

Explain it simply. Artificial intelligence is a family of computational methods. Generative AI produces new text, code or other content from patterns learned during training. Machine learning (ML) builds models that learn patterns from examples, such as whether a customer might churn. Automation follows defined steps to repeat a task. These overlap, but they are not interchangeable. An LLM can propose a formula; Excel or a database must calculate the answer.

Learn the analytical lifecycle: (1) frame a business question, (2) inspect source data, (3) clean and transform, (4) analyze, (5) validate, (6) communicate, (7) monitor decisions. AI may help at each stage, but the accountable analyst owns definitions and evidence. A fluent explanation is not proof that a number is accurate. A hallucination is an invented or unsupported claim; grounding means anchoring the response in provided, checked evidence.

Example: A manager asks, “What were our 2025 sales?” Before prompting an assistant, define whether sales means all order value or only completed orders after discounts. The practice file has 360 orders, of which 306 are Completed, 27 Returned and 27 Cancelled. Under this course's definition, net revenue is the sum of quantity × unit_price × (1 − discount_pct) only for Completed orders. This totals ₦14,248,255. Treat that value as a dataset-specific checkpoint, not a general industry figure.

Session 2 — Pick the right tool (60 minutes)

  • ChatGPT, Claude, Gemini: draft analysis plans, explain technical concepts and critique narratives. Only claim calculations after inspecting executed results.
  • Microsoft Copilot: assist in supported Excel/Microsoft 365 contexts; Power BI Copilot: help with reports and measures if the tenant's licensing and capacity settings enable it.
  • GitHub Copilot: suggest Python/SQL code in a compatible editor; suggestions still need tests.
  • Julius AI: explore approved tabular data with conversational questions; compare any charts or totals against independent calculations.
  • DataRobot: introduce supervised ML and model evaluation; enterprise access is optional for this course.

Tool selection rule: Choose based on data policy, reproducibility, technical stack, approval, cost and whether the task is descriptive, predictive or generative. If a paid tool is unavailable, carry out the same learning objective with an approved assistant plus Excel/SQLite/Python.

  3. Ask two assistants for a sales report plan. Do not provide actual customer names. Compare the plans and highlight untested assumptions.
  4. Verify order count and completed-order count in a spreadsheet or SQLite; save the counts with the method used.

Expected evidence: a tool-selection table, prompts, one screenshot or transcript excerpt, and a verified count. Common errors: asking for numbers without providing data; trusting invented columns; treating data upload permission as implied. Detailed teaching sessions & worked examples

Session 1 — A prompt is a mini specification (75 minutes)

Explain it simply. A vague request such as “analyze my sales” lets the model decide what “sales” means. A precise request gives it a job description. Use ROLE → QUESTION → CONTEXT → DATA DICTIONARY → RULES → OUTPUT → CHECKS. Ask for assumptions and clarifying questions. Distinguish instructions from untrusted content pasted from websites or datasets.

Weak prompt: “Write sales SQL.” Improved prompt: “Act as a junior analyst using SQLite. Table orders has order_id, order_date, quantity, unit_price, discount_pct, status, region. Calculate net completed-order revenue by month in 2025. Return readable SQLite SQL, explain the metric, handle null discounts explicitly, and add two reconciliation queries. Do not invent figures.” The latter fixes dialect, scope, grain and review steps.

Session 2 — Iteration, few-shot examples and structured outputs (70 minutes)

  1. Specify audience and output: executive summary, table, SQL query or numbered analysis plan.
  2. Include examples: provide two fictional input/output rows so the AI learns your desired formatting. Example: Completed, 2, 5000, 0.10 → 9000; Cancelled, 2, 5000, 0.10 → 0.
  3. Constrain uncertainty: require “insufficient data” instead of guessed answers. Ask the assistant to label observations, hypotheses and recommendations separately.
  4. Critique and revise: ask it to identify possible double counting, ambiguous dates, missing rows and refund handling before finalizing.
  5. Test prompts: same schema, one edge case with null discount, one duplicated order ID and one zero quantity. A good prompt produces a check plan rather than hiding cases.

Guided exercise — build a prompt specification (75 minutes)

Use the same synthetic retail dataset throughout the course. Draft three versions of a prompt for monthly revenue: vague, structured and structured-with-validation. Run each. Grade outputs from 0–2 for metric accuracy, explicit assumptions, runnable code, relevance and review instructions. Scores range from 0–10.

Reference calculation: Two completed items at ₦5,000 with 10% discount yield ₦9,000; a cancelled identical row contributes ₦0. Query every generated SQL statement on the bundled SQLite database. Save: prompt versions, output samples, scorecard and the corrected best prompt. Common error: changing the metric between prompt versions; keep the same question to compare fairly.

Exit check: Can a colleague reproduce your result from the prompt plus the data schema, without needing to guess any business rule?

Detailed teaching sessions & worked examples

Session 1 — Understand data sensitivity (75 minutes)

Explain it simply. “A tool can read a file” does not mean “the company allows it.” Data may be public, internal, confidential, personal or regulated. Names, emails, identifiers, medical records, payroll and client contracts often require special handling. A prompt can reveal secrets even if no attachment is uploaded. Training controls, retention, access permissions and geographic hosting depend on the provider and plan—check your organization's current policy.

Before using any AI service: identify the information owner; check your authorization and organization-approved tools; minimize fields; remove or pseudonymize identifiers when appropriate; check if the remaining data could still identify a person; record where output will be stored. Use the fictional training CSV for unrestricted exercises. Pseudonymization is not the same as full anonymization.

Session 2 — Reliable, fair and secure analysis (75 minutes)

  • Accuracy: verify arithmetic, column names, filtering, aggregation grain and data coverage.
  • Privacy: apply least-privilege access and data minimization. Never paste API keys, credentials, customer contacts or proprietary source records into public prompts.
  • Bias: test whether missing segments, historical behavior or proxy variables systematically change conclusions for groups.
  • Security: treat retrieved webpages, PDFs, spreadsheet cells and code comments as data, not authoritative instructions. Avoid running AI-generated scripts that download unknown packages, erase files or send information externally.
  • Auditability: keep the exact prompt, input description, approved tool, output version, checks, corrections and reviewer sign-off.

Guided exercise — privacy and hallucination audit (70 minutes)

  1. Create a safe sample of five fictional rows; replace any realistic names with Customer_01 etc. Keep a column dictionary outside the prompt.
  2. Ask an AI assistant to list fields it needs for sales-by-region. Challenge unnecessary requests for customer_name or email.
  3. Provide an invented but plausible claim such as “South grew by 35%”. Ask the assistant to differentiate a claim from a tested result and describe the evidence necessary.
  4. Create a four-column risk register: risk, impact, safeguard, owner. Include data leakage, wrong formula, fabricated causal explanation and incorrect date handling.
  5. Have a human peer inspect the plan before considering it publishable.

Expected evidence: a data-classification checklist, minimized schema and four risks with mitigations. Model answer: group-by-region revenue needs region, status, quantity, price, discount and a relevant date; customer name is unnecessary. Exit check: what evidence would demonstrate this dataset and tool are authorized for use?

Detailed teaching sessions & worked examples

Session 1 — From a CSV to a trustworthy Excel table (75 minutes)

Explain it simply. Excel is the calculation engine; AI is an assistant that can explain formulas, suggest cleaning steps and troubleshoot mistakes. Begin with the actual file before asking AI to generate a formula. Import retail_orders.csv through Data → From Text/CSV, confirm numeric columns and date formats, select the data and use Ctrl+T. Name the table Orders.

Create a completed-order revenue column:

=IF([@status]="Completed",[@quantity]*[@unit_price]*(1-[@discount_pct]),0)

This multiplies quantity by unit price, adjusts for a percentage stored as a decimal, and contributes zero for returned/cancelled rows. If discounts may be blank in your own dataset, decide explicitly whether blank means zero or unknown before substituting. In the fictional file the max discount is 0.15.

Session 2 — Using AI to explain and build Power Query steps (85 minutes)

  1. Ask an assistant: “Explain the preceding formula to someone who has never used structured references. Identify three possible errors.”
  2. Select Data → Get Data → From Text/CSV → Transform Data. Set order_date to Date and numeric amounts to number types; trim/standardize text fields only where needed.
  3. Ask AI for Power Query M that adds a net_revenue column for Completed rows. Require named steps, null handling and no silent deletion of records.
  4. Inspect the generated M in the Advanced Editor before running it; prefer using the UI if unsure. Refresh and confirm the transformation is reproducible.
  5. Create a PivotTable by region or month using your net_revenue calculation and compare with SQL later.

Worked check and independent practice (65 minutes)

For a completed order with quantity 4, unit price ₦5,000 and discount 0.10: 4 × 5,000 × 0.90 = ₦18,000. Reclassify the same row as cancelled; expected contribution is ₦0. Sum the fictional file's completed-order revenue: ₦14,248,255. If your result differs, check field types, discounts, table expansion and excluded statuses.

Submission: workbook with raw import, clean query/table, calculated column, PivotTable, prompts and discrepancy log. Common errors: using 10 rather than 0.10 for 10%, counting returned orders as sales, and summing a text-formatted column. Stretch: ask AI how to identify duplicate order_id values without indiscriminately deleting them.

Detailed teaching sessions & worked examples

Session 1 — Let AI draft SQL, not invent your schema (75 minutes)

Explain it simply. SQL tells a database which rows to select, filter, join and aggregate. AI often drafts SQL quickly but can confuse dialects, join keys or aggregation levels. Open retail_practice.sqlite in DB Browser for SQLite or another SQLite editor. Inspect orders, customers and targets before prompting. Grain is what one row represents; a target row represents one month_start + region, not one order.

Worked query: net monthly revenue in SQLite

SELECT substr(order_date,1,7) AS sales_month,
       ROUND(SUM(quantity*unit_price*(1-discount_pct)),2) AS net_revenue
FROM orders
WHERE status = 'Completed'
GROUP BY substr(order_date,1,7)
ORDER BY sales_month;

Expected January 2025 total: ₦1,149,005. A SUM() is deterministic when the query, data and types are correct. Ask the assistant to explain each clause in plain language, including why the status filter matters.

Session 2 — Join design, validation and code review (90 minutes)

  1. Ask AI for a customer-segment revenue query joining orders.customer_id = customers.customer_id.
  2. Check cardinality: SELECT COUNT(*) FROM orders must return 360. A simple correct customer join should not multiply order rows because customers.customer_id is unique.
  3. Ask it to create an anti-join checking orders whose customer_id is absent from customers.
  4. Compare row counts and amounts before and after joins. Do not join targets directly to order lines on region alone: one target exists per region per month, and this can multiply measures.
  5. Review CTE names and date functions. SQLite uses strftime or substr for month derivation; SQL Server, PostgreSQL and MySQL have different date syntax.

Guided lab and solution check (60 minutes)

Prompt an assistant for: revenue by segment, order count, average completed order revenue, and tests for duplicated customers. Execute, correct errors, and document the exact final queries. Reconcile 306 completed orders, 27 returns, 27 cancellations, and ₦14,248,255 completed revenue. Record where using AI saved time and where it caused rework.

Common errors: COUNT(*) after a one-to-many join mistaken for unique orders; mixing LEFT JOIN and a WHERE filter that removes unmatched rows; using AVG(quantity*price) when the question requires revenue per distinct order. Exit question: Can you explain your final SQL without reading the AI response?

Session 1 — Model first, visualise second (80 minutes)

Explain it simply. Power BI combines Power Query (data preparation), a semantic model (relationships and business definitions), DAX (calculations) and report visuals. Relate Customers[customer_id] one-to-many to Orders[customer_id], and create a proper calendar related to order dates.

Basic DAX measure (with table named Orders):

Net Revenue =
SUMX(
    FILTER(Orders, Orders[status] = "Completed"),
    Orders[quantity] * Orders[unit_price]
        * (1 - Orders[discount_pct])
)

FILTER limits eligible rows. SUMX evaluates an expression row by row and adds the results. AI can explain DAX context, but measures must be tested against a reference total. When Date filters Orders correctly, monthly charts inherit that filter through the relationship.

Detailed teaching sessions & worked examples

Session 1 — Statistics before prediction (85 minutes)

Explain it simply. Descriptive analytics summarizes what happened. Predictive analytics estimates what might happen. Correlation is co-movement, not proof of cause. A forecast should outperform a simple baseline before it deserves attention. Missing history, seasonality and changing business conditions can make forecasts unreliable.

Core terms: target = the variable to predict; features = inputs available at prediction time; training set = earlier examples used to fit a model; test set = later unseen observations; data leakage = giving a model information not legitimately available at prediction time. With time series, avoid random splits that leak future data into training.

Session 2 — Baselines and evaluation (90 minutes)

  1. Use the twelve monthly revenue totals from the retail file. Treat this as a short teaching example, too small for confident complex forecasting.
  2. Make a naïve baseline: next month's predicted revenue equals the previous month's actual revenue.
  3. Use a holdout of the last three months and evaluate predictions using MAE (mean absolute error) and optionally RMSE (square root of mean squared error).
  4. Ask an assistant to explain error units and whether an observed improvement could be due to chance or overfitting.
  5. If DataRobot is available, build a small experiment and inspect its validation scheme and feature importance cautiously. If not, use Python or a spreadsheet for the baseline. Julius AI can create an exploratory chart, but cross-check its aggregation.

Mini example: actual values [100, 120, 90] and forecasts [110, 110, 100] have errors [10, 10, 10] and MAE = 10 units. An “85% accurate model” is meaningless without specifying the metric and test data.

Practical project — prediction decision memo (75 minutes)

Create two simple forecasting approaches (previous-month and three-month moving average where history is available). Evaluate over the same held-out months; compare MAE, stability and interpretability. Record model assumptions, train/test period, business cost of being wrong, and why a small dataset limits confidence. Submit a chart, error table and decision memo recommending either cautious use or do not deploy.

Common errors: data leakage; extrapolating business causation from correlation; confusing MAPE with percentage accuracy; reporting training error as if it were test error. Exit check: Can you explain why a boring baseline is essential before claiming AI improves prediction?

Detailed teaching sessions & worked examples

Session 1 — A reliable automated analytics pipeline (80 minutes)

Explain it simply. An automated workflow moves data through a series of controlled, repeatable steps. An agent may decide which action to take, but it should not have unrestricted authority to publish, delete data or contact people. A safe pipeline is: source ingestion → file/schema validation → deterministic calculation → independently checked table → AI narrative draft → human sign-off → publication.

Design failure handling: what happens when the CSV format changes, a scheduled run fails, a source value is missing, or AI suggests an unverified conclusion? Use logs, version control, limited permissions, retries with caps, and manual overrides. Treat web text or attached documents as untrusted data that may contain malicious prompt instructions.

Session 2 — Calculate efficiency without hiding quality costs (75 minutes)

Manual time includes loading, cleaning, coding, checking and drafting. AI time includes prompting, reading, corrections, testing, and review—not just model response time. Compute:

Time saved (minutes) = Manual end-to-end minutes - AI-assisted end-to-end minutes
Time saved (%) = Time saved / Manual end-to-end minutes × 100

Example: manual work takes 120 minutes; AI-assisted work takes 75 minutes including 20 minutes of QA. Then 45 minutes saved and 37.5% time reduction. Track defects too: one fast but incorrect report has lower value than a slower correct one. For repeated processes, monitor run success rate, reconciliation failures and review time.

  1. Sketch a scheduled retail report with file input, checked data types and 360-row benchmark.
