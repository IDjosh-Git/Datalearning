Power BI Foundations & Interface

Understand how Power BI works before building anything.

Beginner

1. What Power BI Is

  • Power BI Desktop is used to build data models and reports.
  • Power BI Service is used to publish, share, refresh, and collaborate.
  • A report contains pages and visuals; a dashboard in the Service is a different object built from pinned tiles.
  • The normal workflow is Source → Power Query → Model → DAX → Visuals → Publish.

2. Main Desktop Areas

  • Home ribbon for data connections and common actions.
  • Report view for designing report pages.
  • Model view for relationships and model structure.
  • Data/Table view for inspecting loaded tables.
  • Fields/Data pane, Filters pane, Visualizations/Build pane.

3. Files and Saving

  • .pbix is the standard Power BI Desktop report file.
  • Save versions during learning so mistakes are reversible.
  • Understand that importing data stores model data inside the PBIX.
  • Keep source files in a stable folder if they will be refreshed later.

4. First Visual

  • Load a simple Excel table.
  • Create a Card using Revenue.
  • Create a bar chart using Region and Revenue.
  • Change a visual title.
  • Save the report.

🎯 Week Goal

Open Power BI confidently, understand the main views, and know the journey from source data to a report.

  2. Create a blank PBIX named PowerBI_Practice.pbix.

Power Query for Data Cleaning

Prepare messy source data before it reaches the model.

Data Preparation

1. Power Query Editor

  • Open with Transform Data.
  • Queries appear on the left; Applied Steps appear on the right.
  • Each transformation creates a step.
  • Power Query changes the imported result, not the original Excel/CSV source file.

2. Core Cleaning Operations

  • Remove unwanted rows and columns.
  • Rename columns clearly.
  • Change data types.
  • Replace values.
  • Trim and clean text.
  • Remove duplicates only when logically correct.

3. Shape Data

  • Split columns by delimiter.
  • Merge columns when necessary.
  • Add conditional columns.
  • Fill down or fill up when source structure requires it.
  • Filter rows before loading unnecessary records.

4. Close & Apply

  • Close & Apply loads the transformed result into the model.
  • Changing an earlier step can affect later steps.
  • Refresh reruns the query steps against the source.

🎯 Week Goal

Use Power Query to clean and shape data with repeatable transformation steps.

🧪 Weekly Practice

  1. Load a messy CSV or Excel table.
  2. Remove two unnecessary columns.
  3. Correct Date and Currency data types.
  4. Trim a text column.
  5. Replace inconsistent region names.
  6. Close & Apply and check the model.

💡 Teaching Tip

Always inspect data types. Wrong types are a common cause of broken DAX, relationships, and date analysis.

Detailed Learning Sessions

Week 2 introduces the Power Query Editor. Learners should understand that transformations are recorded as steps and can be repeated automatically whenever the source is refreshed.

Session 1 • 75 minutes
Understanding Query Steps
Explain it simply: Power Query is a recipe. You perform cleaning steps once, Power BI records the recipe, and Refresh repeats that recipe on new data.
Step by step
  1. Load a table and choose Transform Data instead of Load.
  2. Rename the query to Sales.
  3. Inspect Applied Steps.
  4. Rename one column and notice the new step.
  5. Remove one column and notice another step.
  6. Select an earlier step to see the data at that stage.
Worked example: Changing 'Amt' to 'Revenue' creates a reproducible transformation rather than manually editing every future file.
Learner task: Delete one transformation step and observe how the preview changes.
Common mistake: Editing the source Excel manually each month instead of building repeatable Power Query steps.
Session recap: A good query tells a clear transformation story from Source to final clean table.
Session 2 • 90 minutes
Cleaning Text, Numbers and Dates
Explain it simply: Power BI calculations depend on correct data types and consistent values.
Step by step
  1. Select a Region column and use Transform → Format → Trim.
  2. Replace 'NORTH ' and 'north' with consistent labels where needed.
  3. Set Date to Date type, Quantity to Whole Number, Revenue to Decimal/Fixed Decimal as appropriate.
  4. Filter out truly invalid rows.
  5. Use Remove Duplicates only after deciding which columns define a duplicate.
Worked example: Revenue stored as Text cannot be summed correctly until its type is changed to numeric.
Learner task: Create a deliberately messy 20-row table and clean it in Power Query.
Common mistake: Replacing blanks with zero without understanding what blank means can corrupt the analysis.
Session recap: Cleaning is a business decision, not only a technical action.
Session 3 • 75 minutes
Splitting, Conditional Columns and Refresh
Explain it simply: Power Query can reshape a source so the model receives clear fields.
Step by step
  1. Split a combined field such as 'Lagos-South' by delimiter.
  2. Create a Conditional Column classifying Revenue as High/Regular.
  3. Rename the generated columns.
  4. Close & Apply.
  5. Add new rows to the source file.
  6. Refresh Power BI and confirm the same transformation steps are repeated.
Worked example: Source value 'Lagos-South' becomes separate City='Lagos' and Zone='South' columns.
Learner task: Add five new messy source rows, refresh, and verify the transformations handle them correctly.
Common mistake: Hard-coding a one-time manual correction in the source rather than fixing the transformation logic.
Session recap: Refresh should reproduce the same clean structure without manual rework.

Data Modeling & Star Schema

Build a model that is easy to calculate, filter, and maintain.

Modeling

1. Fact vs Dimension

  • Fact tables contain transactions or events.
  • Dimension tables describe entities such as Date, Product, Customer, Region.
  • Facts usually contain numeric measures and foreign keys.
  • Dimensions should have a unique key for each member.

2. Star Schema

  • Place the fact table in the centre.
  • Connect dimensions around it.
  • Prefer one-to-many relationships from dimension to fact.
  • Avoid unnecessary dimension-to-dimension chains for beginner models.

3. Relationship Concepts

  • Cardinality: one-to-many, one-to-one, many-to-many.
  • Filter direction controls how filters propagate.
  • Active relationships are used by default.
  • Keys must have matching data types.

4. Model Hygiene

  • Hide technical key columns from report users when appropriate.
  • Use friendly table/column names.
  • Set default summarization appropriately.
  • Organize measures separately when the model grows.

🎯 Week Goal

Understand fact tables, dimension tables, keys, and one-to-many relationships.

Session 2 • 90 minutes
Relationships and Cardinality
Explain it simply: A relationship lets a selection in one table filter matching rows in another.
Step by step
  1. Open Model view.
  2. Drag DimProduct[ProductID] to FactSales[ProductID].
  3. Confirm one-to-many cardinality.
  4. Repeat for Region.
  5. Create a table visual with Product Name and Revenue.

Building a Clean Star Schema
Explain it simply: A star schema makes DAX simpler and filter behavior easier to predict.
Step by step
  1. Arrange dimensions around FactSales in Model view.
  2. Rename tables clearly.
  3. Hide foreign-key columns that report consumers do not need.
  4. Set appropriate formatting for numeric columns.
  5. Create a Region slicer and Product chart to test cross-filtering.
Worked example: A model with DimDate, DimProduct, DimCustomer and DimRegion around FactSales is easier to reason about than one huge flat table with repeated labels.
Learner task: Draw the model on paper before creating it in Power BI.
Common mistake: Using bidirectional relationships everywhere can create ambiguous filtering.
Session recap: A clean model is part of report design, not an optional technical step.

DAX Measures & Core Calculations

Create business metrics that respond to report filters.

DAX

1. Measures vs Columns

  • Calculated columns are computed row by row and stored in the model.
  • Measures are calculated at query time based on filter context.
  • Most report KPIs should be measures.
  • Use explicit measures instead of relying only on implicit visual sums.

2. Basic Measures

  • SUM, COUNTROWS, DISTINCTCOUNT, DIVIDE.
  • Revenue, Cost, Profit, Orders, Customers.
  • Use meaningful names and consistent formatting.

3. CALCULATE

  • CALCULATE evaluates an expression under modified filter context.
  • It is central to DAX.
  • Simple filters can be applied inside CALCULATE.
  • Later time-intelligence measures rely heavily on CALCULATE.

4. Filter Context

  • Slicers create filter context.
  • Rows/columns in a visual create filter context.
  • Measures recalculate for each context.
  • The same Total Revenue measure can show a grand total, regional total, or product total.

Session 1 • 75 minutes
Measures vs Calculated Columns
Explain it simply: A column gives every row a stored value. A measure gives the report a result based on the current selection.
Step by step
  1. Create a calculated column Profit Row = Revenue - Cost.
  2. Create a measure Total Profit = SUM(FactSales[Profit Row]).
  3. Put Region in a matrix and Total Profit in Values.
  4. Observe the measure changing for each Region and the total.
Worked example: A sales row may have Profit=2,000. The Total Profit measure adds only the rows visible in the current filter context.
Learner task: Ask whether 'Total Revenue' should be a measure or column and explain why.
Common mistake: Creating many calculated columns for totals can increase model size and produce the wrong level of calculation.
Session recap: Use columns for row-level attributes and measures for aggregations/business metrics.
Session 2 • 90 minutes
Core Business Measures
Explain it simply: Measures should be small, reusable building blocks.
Step by step
  1. Create Total Revenue.
  2. Create Total Cost.
  3. Create Total Profit as [Total Revenue] - [Total Cost].
  4. Create Total Orders with DISTINCTCOUNT(OrderID).
  5. Create Profit Margin using DIVIDE.
  6. Format currency and percentage measures.
Total Revenue = SUM(FactSales[Revenue]) Total Cost = SUM(FactSales[Cost]) Total Profit = [Total Revenue] - [Total Cost] Total Orders = DISTINCTCOUNT(FactSales[OrderID]) Profit Margin % = DIVIDE([Total Profit], [Total Revenue], 0)
Learner task: Put all five measures into Cards and verify the values under Region and Product slicers.

Session 3 • 90 minutes
CALCULATE and Filter Context
Explain it simply: CALCULATE changes the filter context used to evaluate an expression.
Step by step
  1. Create a measure for Completed Revenue using CALCULATE.
  2. Create a visual with Region and both Total Revenue and Completed Revenue.
  3. Filter one Region and observe both measures.
  4. Explain that the visual, slicer, and DAX filter all contribute context.
Completed Revenue = CALCULATE([Total Revenue], FactSales[Status] = "Completed")
Worked example: If a Region slicer selects West, Completed Revenue returns only completed West transactions.
Learner task: Create High Value Revenue where Revenue rows are greater than a chosen threshold.
Common mistake: Thinking a measure has one permanent answer. Its answer depends on filter context.
Session recap: The same measure can legitimately return many values depending on the report context.

Date Tables & Time Intelligence

Compare performance across months, years, and prior periods.

Time Intelligence

1. Why a Date Table

  • A dedicated date dimension gives one row per date.
  • It supports Year, Quarter, Month, Week and other attributes.
  • Marking the table as a Date table clarifies the date column.
  • Relate DimDate[Date] to the fact date.

2. Useful Date Columns

  • Year, Quarter, Month Name, Month Number.
  • Sort Month Name by Month Number.
  • Year-Month labels are useful for charts.
  • Avoid alphabetical month sorting.

3. Time Measures

  • YTD with TOTALYTD or DATESYTD patterns.
  • Previous Year with SAMEPERIODLASTYEAR.
  • Year-over-Year variance.
  • YoY % using DIVIDE.

4. Testing Time Logic

  • Use a matrix by Year and Month.
  • Check partial-year behavior.
  • Verify totals against source data.
  • Make sure the relationship uses the intended transaction date.

Build a proper Date table and create measures for YTD, previous year, and variance.

Week 5 teaches one of the most important analytical patterns: time. Learners need a continuous Date table so monthly, yearly and prior-period calculations behave consistently.

Session 1 • 90 minutes
Creating a Date Table
Explain it simply: A Date table is a calendar that filters the fact table consistently.
Step by step
  1. Create DimDate using CALENDAR or CALENDARAUTO.
  2. Add Year, Month Number, Month Name and Quarter.
  3. Sort Month Name by Month Number.
  4. Mark DimDate as a Date table using the Date column.
  5. Create a one-to-many relationship to FactSales[OrderDate].
DimDate = ADDCOLUMNS( CALENDAR(DATE(2025,1,1), DATE(2027,12,31)), "Year", YEAR([Date]), "Month No", MONTH([Date]), "Month", FORMAT([Date], "MMM"), "Quarter", "Q" & FORMAT([Date], "Q") )
Common mistake: Using the fact table's text Month field for all time analysis can lead to bad sorting and incomplete calendars.
Session recap: A Date dimension centralizes time filtering.
Session 2 • 90 minutes
YTD and Previous-Year Measures
Explain it simply: Time intelligence re-evaluates a base measure over a different date range.
Step by step
  1. Create Revenue YTD.
  2. Create Revenue Previous Year.

Practical Intermediate DAX

Add ranking, averages, target comparisons, and dynamic report behavior.

Intermediate DAX

1. Iterators

  • SUMX evaluates an expression row by row over a table.
  • AVERAGEX averages an expression over rows.
  • Use iterators when the result must be computed from row-level expressions.

2. Ranking

  • RANKX can rank Products, Salespeople or Regions.
  • Ranking responds to filter context.
  • Use ALL or ALLSELECTED carefully depending on desired scope.

3. Target & Variance

  • Actual vs Target.
  • Variance = Actual - Target.
  • Variance % = Variance / Target.
  • Use conditional formatting for performance.

4. Dynamic Text

  • SELECTEDVALUE can display current selection.
  • Measures can create dynamic titles.
  • Avoid confusing users when multiple selections are active.
